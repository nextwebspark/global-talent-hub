REPLIT PROMPT — Enhanced AI Search & Talent Mapping Intelligence

You are working on an existing Talent Mapping application built with React 19 + TypeScript (Vite, Tailwind CSS, Radix UI/shadcn, Wouter, TanStack Query, Zustand, Framer Motion) on the frontend, and Node.js + Express (TypeScript, tsx) with PostgreSQL via Drizzle ORM on the backend. The AI pipeline uses both OpenAI and Anthropic SDKs. Everything shares types via shared/schema.ts.
You are going to completely replace the existing search page and its underlying pipeline with a significantly more intelligent, high-value system. Do not break any other part of the application. Work through this systematically — schema first, then backend, then frontend.

PART 1 — DATABASE SCHEMA CHANGES (shared/schema.ts and migration)
Extend the existing schema with the following. Do not delete existing tables — only add new columns and tables.
On the existing search results / company table, add these columns if they do not already exist:

relevanceType — enum: 'direct' | 'adjacent' | 'inferred'
relevanceRationale — text: one sentence explaining why this company was included
confidenceScore — integer 1–100
sector — text
subSector — text
geography — text (country or region)
companySize — text (e.g. "500–5,000 employees")
revenueRange — text
isUserAccepted — boolean, default false
isUserRejected — boolean, default false
searchSessionId — foreign key to a new searchSessions table

Create a new searchSessions table with:

id, userId, createdAt, updatedAt
rawQuery — the original text the user typed
pdContent — nullable text (extracted text from uploaded PD document)
inferredIntent — JSON object (see structure below)
status — enum: 'running' | 'complete' | 'failed'
refinementHistory — JSON array of refinement messages

The inferredIntent JSON object must follow this structure exactly:
ts{
  primarySectors: string[],
  adjacentSectors: string[],
  inferredSectors: string[],
  targetGeographies: string[],
  companySizeRange: string,
  seniorityLevel: string,
  roleFunction: string,
  keyResponsibilities: string[],
  exclusions: string[],
  searchRationale: string, // 2–3 sentence explanation of what the AI understood
  confidenceInInterpretation: number // 1–100
}
Run the Drizzle migration after making these changes.

PART 2 — BACKEND AI PIPELINE (server-side)
Replace the existing search pipeline with the following multi-step streaming pipeline. The pipeline must emit Server-Sent Events (SSE) so the frontend receives live progress updates at every step. Each SSE event has a type field and a data payload.
SSE event types to emit:

intent_extracted — emitted after step 1, payload is the full inferredIntent object
company_found — emitted each time a single company is discovered, payload is a partial company object
company_enriched — emitted when a company's metadata is filled in (sector, size, rationale, confidence), payload is the enriched company object
adjacent_sector_found — emitted when an adjacent or inferred sector search begins, payload includes sector name and rationale for why it was included
executive_found — emitted when a senior executive is found at a discovered company
refinement_applied — emitted when the user sends a refinement message and the AI re-interprets
search_complete — emitted when all steps are done, payload includes summary stats
error — emitted on any failure with a message

The pipeline must execute in this order:
Step 1 — Deep Intent Extraction
Use Claude (claude-opus-4-5 or best available Anthropic model) for this step. It is the most important step.
Send the user's raw query AND any uploaded PD content to Claude with this system prompt logic:
You are an expert Talent Acquisition research analyst with deep knowledge of global industries, sectors, and executive talent markets. Your job is to deeply understand what a TA professional is looking for when they submit a search query or position description.
Analyse the input and extract a structured intent object. Be highly specific about sectors — do not use vague terms like "technology." Say "B2B SaaS — Supply Chain Software" or "FMCG Distribution — GCC Region" instead.
For adjacentSectors, think like a senior headhunter: which other industries have deep concentrations of people with the same skills, responsibilities, and commercial experience? Always provide 3–5 adjacent sectors with a one-line rationale for each.
For inferredSectors, go one level further — what non-obvious sectors might contain the right talent profile? These are the "out of the box" additions a great researcher would suggest.
If a company name is present in the query or PD, identify its exact industry and use that as the anchor for all sector inference.
If the document is confidential (no company name), infer sector from the specific responsibilities, KPIs, reporting lines, and commercial context described.
Return only valid JSON matching the inferredIntent schema. No preamble, no explanation outside the JSON.
Emit intent_extracted SSE event with the result.
Step 2 — Primary Company Search
Use the existing Serper web search integration. Run searches for companies in primarySectors × targetGeographies. For each company discovered, immediately emit a company_found SSE event so the frontend can display it in real time. Do not wait for all companies to be found before emitting.
Step 3 — Company Enrichment
Use OpenAI (gpt-4o) for this step. For each discovered company, extract and enrich: sector, sub-sector, geography, company size, revenue range, relevance type, confidence score, and a one-line relevance rationale. Emit company_enriched for each company as it completes.
Step 4 — Adjacent and Inferred Sector Search
Repeat Step 2 and Step 3 for adjacentSectors and inferredSectors. Tag all results with their relevanceType (adjacent or inferred). Emit adjacent_sector_found before beginning each new sector search so the user can see the AI expanding its thinking.
Step 5 — Executive Search
For the top companies by confidence score (limit 20 to manage performance), run executive extraction. Use the existing executive search logic but ensure results are tagged to their parent company and search session. Emit executive_found for each result.
Step 6 — Deduplication, Validation and Persistence
Deduplicate companies by name and domain. Validate against the original inferredIntent. Save everything to the database under the searchSessionId. Emit search_complete.
Refinement endpoint:
Create a separate POST /api/search/refine endpoint that accepts { sessionId, refinementMessage }. It passes the refinement message plus the existing inferredIntent to Claude, produces an updated inferredIntent, appends the message to refinementHistory, and triggers a new targeted search pass for only the changed criteria. Stream results back via SSE in the same format.
PD Upload endpoint:
Create POST /api/search/upload-pd that accepts multipart form data. Support PDF (use pdf-parse), DOCX (use mammoth), and plain text. Extract the full text, store it in the session as pdContent, and return the extracted text to the frontend for confirmation display. Do not run the search yet — wait for the user to confirm and submit.

PART 3 — FRONTEND (replace the existing search page entirely)
Replace the current search page with a new full-page experience. The design must feel premium, intelligent and purposeful — not like a standard search bar. Use the existing Tailwind, Radix UI, Framer Motion, and TanStack Query setup throughout.
The page has three distinct states:

Layout: Centred, generous whitespace. This should feel like the start of a strategic conversation, not a Google search box.
